## What this is

**ZHP PMS** (working platform name — originally built as "Zahill PMS" for a single property, now a **multi-tenant Property Management System platform** intended to be sold/hosted for multiple hotel/glamping clients from one shared codebase and database). Zahill is the first, reference property running on the platform; "Birdnest" is a second property used to build and verify multi-tenancy end-to-end. Both run on the same infrastructure, fully data-isolated from each other.

Built as a monorepo with React/Vite frontend(s) and a Node/Express backend shared by every property.

**Owner:** Juppy (juppyjp@gmail.com)

**Product name is now locked: HALF.** Domain/tenancy scheme decided (2026-08-14): a single app subdomain (`half.kdai.cloud`), not one subdomain per client. Every property logs into the same domain; the JWT (already carries `propertyId`) is what resolves tenant, exactly like GitHub/Stripe Dashboard/Google Workspace rather than Shopify-style `client.myapp.com`. Rejected per-client subdomains because it would require wildcard DNS/cert + a Host-header-based login rewrite for no real benefit at current scale (one browser origin is fine since no one needs two properties open in parallel tabs today — superadmin already has its own separate, non-property-scoped auth layer for cross-property work). Module-specific subdomains keep the existing pattern, just moved off `zahill.kdai.cloud` onto `half.kdai.cloud` (e.g. `kitchen.half.kdai.cloud`, `display.half.kdai.cloud`, `tv.half.kdai.cloud`) — small fixed set, no wildcard needed. If a client later wants their own branded custom domain, that's a per-client CNAME added on top of this, not a redesign.

**Not yet done:** this is a naming/architecture decision, not an executed migration — `zahill.kdai.cloud`/`d-zahill.kdai.cloud` are still the live domains, and "Zahill PMS"/"ZHP PMS" still appear throughout code (package names, page titles, MQTT topic namespace, Nginx configs). Renaming those and standing up `half.kdai.cloud` is future work, not done in this pass.

## Multi-Tenancy & Platform Architecture

**This is the core architectural fact about this codebase: it is not single-tenant.** Every property's data lives in the same database, isolated by `property_id`. This was built and verified in migrations **019–026** against a live second property (Birdnest) — full detail in `MULTI_TENANCY.md`.

### How isolation works
- Every business table has a `property_id` column (added in `019_multi_tenancy.sql`).
- Every authenticated route reads `req.propertyId` (set by `middleware/auth.js` from the JWT — see below) and every query is scoped `WHERE property_id = $n`.
- The JWT issued at login (`routes/auth.js`) embeds `propertyId` alongside `userId`/`role`. `middleware/auth.js` decodes it and sets `req.propertyId` on every request.
- Formerly-singleton tables (`property_settings`, `ai_market_summary` — used to be `WHERE id = 1`) are now one row per property, scoped by `property_id` with a unique constraint instead of a hardcoded PK.
- Tables with human-readable string IDs that used to be globally unique (`booking_sources`, `payment_methods`, `roles`) are now namespaced per property (`<id>-<property_uuid>`) so two properties can both have a role called `manager` without colliding. `users.role`, `bookings.source`, `payments.method` were widened to `varchar(50)` in migration `026` to fit these namespaced values.

### Superadmin & property onboarding
A superadmin is a platform-level operator, not tied to any one property (`users.is_superadmin = true`, `property_id` nullable for them). Distinct auth layer: `middleware/authSuperAdmin.js`, mounted at `/api/admin` in `server/index.js`, ahead of and separate from the per-property `auth` + `moduleGuard` chain.

`routes/admin.js` endpoints:
- `GET /api/admin/properties` — list all properties + module counts
- `POST /api/admin/properties` — create a property (`name`, `slug`, `plan`, `display_token`), then calls `seedPropertyDefaults(property.id)` to clone default settings/modules/booking-sources/payment-methods/roles in one shot
- `GET /api/admin/properties/:id` — property detail + its module states + branding fields (`logo_url`, `brand_color`, `property_name`, `property_address`, `property_phone`, `property_email`, joined from `property_settings`)
- `PATCH /api/admin/properties/:id` — update name/slug/plan/is_active
- `PATCH /api/admin/properties/:id/modules` — toggle a module on/off
- `PATCH /api/admin/properties/:id/branding` — update brand color + contact/invoice fields on `property_settings` (same columns the property owner can also edit in their own Settings page — both write the same row, last save wins, by design)
- `POST /api/admin/properties/:id/logo` — multipart logo upload (`multer` + `sharp`, resized to 512×512 PNG, saved to `server/uploads/property-logos/`, served unauthenticated at `/property-logos/*` since the login screen, Room/TV Display, and email clients all need it without a JWT)
- `GET /api/admin/properties/:id/users` / `POST /api/admin/properties/:id/users` — manage a property's staff accounts

**Frontend — traced button-by-button against the API above (verified, not assumed):**

`client/src/pages/admin/` (`AdminLayout.jsx`, `Properties.jsx`, `PropertyDetail.jsx`), routed in `App.jsx` at `/admin` and `/admin/properties/:id`, gated by `RequireSuperAdmin` (checks `user.is_superadmin`, redirects to `/login` or `/` otherwise). `Login.jsx` sends a superadmin straight to `/admin` after auth; `AuthContext.jsx` skips the per-property `fetchModules()` call for superadmins since they have no `property_id`.

## MQTT Setup

- Broker: `mqtt.d-zahill.kdai.cloud` port `1883` (Zahill's own broker — each property should get its own broker/credentials; do not share across properties, to avoid cross-property command collisions)
- WebSockets: port `9001`
- Auth: username `zahill`, password configured per `server/.env`
- DNS: `mqtt.d-zahill.kdai.cloud` A record → VM IP
- **Connection is app-wide, not per-property** (`server/mqtt/index.js` — one module-level client for the whole Node process). Only opened at startup if at least one **active** property has `room_controller` **enabled** (`server/index.js`, checked against `property_modules`/`properties` before calling `mqttClient.connect()`) — otherwise it's skipped entirely rather than endlessly retrying a broker nothing needs. `connect()` is idempotent; `PATCH /api/admin/properties/:id/modules` also calls it when `room_controller` is turned on, so enabling the module takes effect immediately without a server restart. (There's currently no matching "disconnect if the last property turns it off" — harmless, since an idle connected client produces no reconnect noise.)

### Topic Structure

**Subscribe (backend → ESP32):**
- `zahill/room/{id}/relay/{n}/set` — payload: `on` or `off`
- `zahill/room/{id}/rgb/set` — payload: `{"r":255,"g":0,"b":0}`
- `zahill/room/{id}/ir/send` — payload: slot index
- `zahill/room/{id}/request/status` — triggers full status publish

**Publish (ESP32 → backend):**
- `zahill/room/{id}/relay/{n}/state` — `on` or `off` (retained)
- `zahill/room/{id}/rgb/state` — JSON (retained)
- `zahill/room/{id}/status` — full JSON snapshot
- `zahill/room/{id}/connected` — `true`/`false` LWT (retained)

## Backend — Current State

**Stack:** Node.js + Express (CommonJS), PostgreSQL (raw SQL), JWT auth, PM2 + Nginx
**Port:** 4000 behind Nginx
**Entry:** `server/index.js` — also where module gating is wired (see Multi-Tenancy section above)

**Route files** (`server/routes/`):
- `auth` — login/logout (always on)
- `public` — unauthenticated endpoints callable pre-login/pre-JWT (e.g. property branding lookup by slug for the login screen)
- `admin` — superadmin: property CRUD, module toggles, per-property user management (separate `authSuperAdmin` layer)
- `units`, `users`, `settings`, `dashboard`, `display` — core, always on (`display` also carries `POST /room/:roomId/telemetry` — the `room-display-kiosk/` Android APK's device-health push, `authDisplay`, no moduleGuard, upserts `room_display_devices`)
- `bookings`, `checkin`, `allotments`, `pricing`, `ratePlans` — reservations + front desk (`ratePlans` = the "arrangement" per booking: RO/BB/HB/FB + a flat net per-pax-per-night meal price; owner CRUD at `/settings/rate-plans`)
- `guests`, `loyalty` — guest CRM
- `payments`, `reports`, `nightAudit`, `folio`, `agents` — financial (`agents` = Agent Accounts / Direct Billing #13: per-agent statement, AR aging, agent payments + allocations, consolidated invoice PDF; owner-only per handler. `reports` = monthly revenue summary — one endpoint, `GET /api/reports/revenue`, night-based room/F&B revenue + daily chart + by-source breakdown; had no client page until `Reports.jsx` closed that gap, see Frontend section)
- `tasks` — operations kanban
- `products`, `sales`, `tables` — ancillary sales, table management (ride on the `sales` module via `modules.js`)
- `kitchen` — Kitchen Display kiosk app's API. `authDisplay` (per-property `display_token`, same as `display`) on every route, not staff JWT — the Kitchen Display is its own kiosk app (`kitchen-display/`), not a page inside the PMS client. `moduleGuard('sales')` applied per-route instead of via `modules.js`.
- `resto`, `restoGuest` — Resto Ordering (`resto-display/`), own `resto_ordering` module. `resto` is the staff surface (`auth`, staff JWT, plus `authQueryToken` for its SSE stream); `restoGuest` is the public guest QR self-order surface, gated by a new per-table credential (`authTableQR`) — deliberately **not** the shared `display_token` (see the write-up below for why). `moduleGuard('resto_ordering')` applied per-route in both files instead of via `modules.js`.
- `board` — Guest Board CMS (In-Room Media)
- `iot` — Room Controller (MQTT-backed device state, ESP32 relay/RGB/IR — hardware-dependent, off by default)
- `calls` — Calling (two-way room↔desk voice, own `calling` module, no hardware dependency — see the Room Display section below for the full write-up)
- `insights` — Market Insights (competitors, trends, AI briefing)
- `communications` — guest email (owner-only)
- `purchasing` — Back Office Slice A (Suppliers, Raw Materials, Purchase Orders + receiving), own `back_office` module, owner-only per handler. See the Back Office write-up below for the full design (why ingredients get their own `raw_materials` table instead of reusing `products`, the PO status workflow, partial receiving).
- `expenses` — Back Office Slice B (categorized cost log — laundry, electricity, maintenance, etc. — plus CSV export), same `back_office` module, owner-only. See the Back Office write-up below.
- `roomTypes` — Room types (`/api/room-types`, always on, not module-gated like `units`): GET any staff, POST/PUT/DELETE owner. PUT pushes name/base_rate/max_guests to every room via trigger; a rename also updates `yield_settings`, `yield_rate_log` and the `Auto: <name>` pricing periods in one transaction; DELETE is blocked while rooms use the type. `POST/PUT /api/units` take `room_type_id` (or a type name that must already exist) and ignore direct rate/capacity edits. `UnitSettings.jsx` is grouped by room type (rate/capacity edited once per type, collapsible groups, + Add Room inside a group).

**Back Office — Slice A (`BackOffice.jsx`, `/back-office`) — implemented 2026-09-13, migration 053.** First slice of the module ROADMAP.md scoped back in 2026-08-17 and never started. New `back_office` module (default off, paid add-on tier). One page, one nav entry, internal tabs (Suppliers / Raw Materials / Purchase Orders) — matching `Sales.jsx`'s tab-switching shape rather than separate routes, so future slices (Expenses, Cash & Bank, Recipes) just add more tabs to the same file. **Real design decision made with the owner mid-plan: raw ingredients (flour, rice, chicken breast — never sold directly) get their own `raw_materials` table, not a repurposed `products` row.** Reusing `products` was considered and rejected — it would have risked an ingredient leaking into a guest menu / staff POS grid / Kitchen Display if a filter were ever missed at any of the several places that already query `products`, and would have mixed future ingredient-cost reporting into the general Sales/Reports domain. `raw_materials` has its own `unit_of_measure` (kg/g/l/ml/pcs), NUMERIC (fractional) `stock_quantity` — unlike `products`' INT stock, since ingredients are bought/consumed in kg/g/l/ml — and its own `raw_material_movements` ledger, fully separate from `stock_movements`. `purchase_order_items` restocks *either* an existing sellable `product` (e.g. bulk-buying bottled water for resale) *or* a `raw_material` (e.g. buying rice for the kitchen) per line, enforced by a `CHECK` that exactly one is set. PO status workflow (`draft → pending_approval → approved → received`, or `cancelled` from any pre-received status) is a whitelist transition map in `server/services/purchasingService.js`; receiving (`POST /purchase-orders/:id/receive`) supports partial receipt across multiple calls, clamped so a line can never be over-received, and only flips the PO to `received` once every line is fully received. Verified against the live dev DB end-to-end — service layer *and* real HTTP round-trips against a running server (create → submit → approve → partial receive → full receive; confirmed `moduleGuard('back_office')` actually 403s while off and succeeds once toggled on). **Slice B — Expenses — implemented 2026-09-13, migration 055.** A lightweight, categorized cost log (laundry, electricity, maintenance, etc.) — explicitly **not** a step toward a full accounting system (GL/chart-of-accounts/journal entries stay out of scope, confirmed with the owner). The design goal instead: a real Net Income view inside the PMS, and data clean enough to hand to an outside accountant. Fixed `CHECK`-constrained `category` (free text was rejected — can't be reliably summed for Net Income or mapped to a chart of accounts by a bookkeeper), `payment_method` validated in-route against `payment_methods` (same convention as `sales.payment_method`, not a DB-level FK), optional `supplier_id` link to the Slice A Suppliers directory, **void-not-delete** (mirrors `folio_charges`, not `agent_payments`' hard-delete — an accountant needs an unbroken audit trail). New `server/routes/expenses.js` (`GET /`, `POST /`, `DELETE /:id` = void, `GET /export` = CSV) — no new module, rides `back_office`. **CSV export is new to this codebase** (every prior download was PDF) — also added to Purchase Orders (`GET /purchase-orders/export`) since an accountant needs both operating costs and inventory purchases; client-side download reuses `Agents.jsx`'s PDF-blob-download shape, just `text/csv`. Caught and fixed a real bug building the PO export: `created_at`/`updated_at` are `TIMESTAMPTZ` (real JS `Date` objects from `pg`, unlike `DATE` columns which `db/index.js` normalizes to plain strings) — `String(date).slice(0,10)` silently grabbed garbage from `Date.prototype.toString()` instead of an ISO date; fixed with `.toISOString().slice(0,10)`. `GET /api/reports/revenue` gained `expenses_total`/`net_income`, surfaced as a new "Net Income" card on `Reports.jsx`; safe for properties that don't use Expenses (an empty table just returns 0, degrading Net Income to "= Total Revenue" rather than erroring). New Expenses tab on `BackOffice.jsx` (fourth tab). Verified end-to-end against the live dev DB and real HTTP round-trips. **Inventory Value — implemented 2026-09-13, migration 056.** Scoped as the deliberate first step before any COGS/Net-Income-from-purchases work — raised by the owner directly: *"before [subtracting purchases], should we also have the value of our inventory stated in the app?"* Correct call — buying inventory is an asset swap, not an expense, until it's consumed (sold), and you can't compute "value consumed" without first knowing "value on hand." `products` gains `cost_per_unit` (weighted-average, same treatment `raw_materials.cost_per_unit` already had from Slice A — `purchasingService.js`'s `receivePurchaseOrder` product branch now blends every PO receipt into the running average the same way the raw-material branch already did, verified with the identical 100@5000+50@6000→5333.33 case proven for raw materials). An item with stock but no `cost_per_unit` yet (never received through a PO) is listed but **excluded from the total**, flagged with a visible warning rather than silently valued at 0. Deliberately **no COGS, no Net Income change, no Recipes** in this pass — those stay future work; this only makes "what's on hand worth" visible. Both displays render the property's own logo/name from that `property` field (falling back to the bundled default asset/text when a property hasn't uploaded one) — see the Superadmin Property Branding trace above.

### 3. Kitchen Display
**Only purpose:** Kitchen ticket board — New/Preparing/Ready columns, tap to advance a ticket. One kiosk per kitchen station, not per-unit.

- Originally shipped as a page inside the PMS client (`/kitchen`, staff-JWT-gated); extracted into its own standalone kiosk app (`kitchen-display/`) to match the Room Display / TV Display pattern — same `display_token` device-auth model instead of staff login, so a kitchen tablet doesn't need a staff account.
- `GET /api/kitchen/active` (ticket board data), `PATCH /api/kitchen/:id/status` (advance a ticket), `GET /api/kitchen/stream` (SSE push on `kitchen:{propertyId}`) — all `authDisplay`, all gated `moduleGuard('sales')` per-route. `authDisplay` reads the token from either the `Authorization` header or `?token=`, so the same middleware covers the SSE endpoint (EventSource can't set custom headers) without a separate query-token middleware. `GET /active` excludes any sale still `confirmation_status='pending'` (a not-yet-confirmed Room Display room-service order — see Resto Ordering below); everything else (QR/dine-in, staff-entered, and confirmed room-service orders) behaves exactly as before.
- Setup screen accepts the same per-property `display_token` used by Room Display and TV Display (surfaced in `SettingsProperty.jsx`'s "Device Setup" card, owner-only, `GET /api/settings/display-token`).
- Stack: React/Vite PWA (`kitchen-display/`), dev port 5177, CORS origin via `KITCHEN_URL` env var. Deployed at `kitchen.zahill.kdai.cloud` per `nginx/kitchen.conf` — kept on the existing `zahill.kdai.cloud` domain for now rather than the planned `half.kdai.cloud` (see "What this is" above); the rename stays deferred until every app is confirmed working on the current domain.
- Removed from the PMS client as part of this extraction: `pages/KitchenDisplay.jsx`, `context/KitchenTicketsContext.jsx`, the `/kitchen` route, the `kitchen_display` menu key (`SettingsRoles.jsx`) and its nav links (`Sidebar.jsx`/`BottomNav`). Staff no longer need a menu permission for it — it's a separate device, not a PMS page.

### 4. Resto Ordering
**Purpose:** Restaurant ordering — a guest QR self-order surface per table, plus a floor-staff app for table-side order-taking, a room-service confirm queue, and table/session management. New paid add-on module `resto_ordering` (default **off**, migration 048), own standalone app `resto-display/` (matches the Kitchen Display extraction precedent — a separate deployable so it can be sold per-property independent of the base `sales` module).

- **Why a confirmation step exists at all, and why it's narrow:** industry research (Toast/Lightspeed) confirmed real POS/KDS systems don't gate orders behind human approval before firing to the kitchen for either self-order or staff-entered orders — their "Expo" role checks completeness *after* prep, not before. The one place a gate earns its keep here is **Room Display's room-service orders specifically** — unlike a table order a waiter is standing next to, nobody at the property has looked at a room-service order before it's submitted. So only `order_source='room_display'` orders land as `sales.confirmation_status='pending'`; QR self-order and staff-entered orders fire straight to `kitchen_status='new'` like before.
- **Two auth models, deliberately different from the shared `display_token`:**
  - Guest QR self-order (`resto-display/`'s `/t/:qrToken` screen) uses a new **per-table** credential — `restaurant_tables.qr_token`, validated by `server/middleware/authTableQR.js`, resolving only to `{propertyId, tableId}`. This is *not* the property-wide `display_token` Room/TV/Kitchen Display share — printing that shared secret on a table (a public surface) would let anyone who scans it reach unrelated endpoints for arbitrary rooms. A table's QR is regenerable independently (`POST /api/resto/tables/:id/qr/reset`, owner-only) without touching any other table or device.
  - Floor staff (`resto-display/`'s `/staff/*` screens) reuse the **existing PMS `users`/`roles`/JWT login as-is** — no new auth system. A restricted role (e.g. `resto_staff`, `allowed_menus: ['resto_take_order']`) limits a shared tablet to only the Take Order screen, via a local reimplementation of the PMS's `allowed_menus`/`RequireMenu` pattern (`resto-display/src/auth.js` — can't import `client/`'s `AuthContext` across separate apps). Shared/generic logins are fine if a client doesn't want per-waiter accounts; the only cost is losing per-order attribution on `sales.served_by`. **Menu-key gating is client-side only for navigation** (same as the PMS: the JWT + `resto_ordering` module gate is all any `/api/resto/*` route requires) — **except for two routes that got real server-side enforcement, added after the client explicitly said the resto domain should own its own menu/tables rather than needing a PMS owner login**: `POST/PUT/PATCH /api/products` and `POST/PUT/DELETE /api/tables` now accept either the `owner` role **or** a non-owner whose `allowed_menus` includes `resto_menu`/`resto_tables` respectively (`server/middleware/requireOwnerOrMenu.js`). This required adding `allowed_menus` to the JWT payload itself (`routes/auth.js`, previously only in the login response body, not the token — same re-login-to-take-effect staleness the client already accepted). Because `products`/`tables` are shared with the PMS Sales page, granting a role `resto_menu`/`resto_tables` also grants product/table mutation rights there, not just in resto-display — worth knowing when assigning these permissions. `qr/reset` stays strictly owner-only (unchanged) since it invalidates a printed sticker immediately.
- **Table sessions** (`table_sessions`, migration 048) group every order from one dining visit so a table's QR always resolves to whatever session is currently active — an old scan can't leak into the next party's visit. A session opens implicitly on a table's first order (guest QR or staff) or explicitly via staff "Seat Party," and closes only via staff "Close Table" / "Settle" (`server/services/tableSessionService.js` + `restoSettleService.js`) — **manual only, no auto-close job**, a deliberate trade-off accepted knowingly: a forgotten table stays "occupied" until a staff member clears it. `restaurant_tables.status` (available/occupied) is kept as a derived flag the session service writes, not a second source of truth.
- **Payment: open tabs, settled at the table (migration 050).** The QR self-order screen has **no payment step** — a walk-in shouldn't have to pay before eating. Guest QR orders *and* staff-entered dine-in orders both land with `sales.payment_method='unpaid'` (a sentinel like `'room_charge'`, not a real `payment_methods` row) and still fire straight to the kitchen. When the party's done, staff hit **Settle** on the table in the resto app (`TablesScreen.jsx`'s bill modal): pick **one** method for the whole session — cash/QRIS/etc, or **Charge to room** (picks from `GET /api/resto/rooms`, the in-house list) — and `restoSettleService.settleAndClose` flips every unpaid non-rejected sale to that method + stamps `settled_at`/`settled_by` + posts folio charges if `room_charge`, then closes the session. One payment per table, no split (scope choice). `POST /api/resto/orders`'s `payment_method` is now optional (omit = open tab); a real method still works for immediate-pay takeaway. `/tables/:id/close` 409s (`code:'UNPAID'`) if anything's still unpaid — settle first. `salesService.createSale` dropped `sales.payment_method`'s old hardcoded `cash`/`qris`/`room_charge` CHECK back in migration 048 and is still the one validation choke point (staff POS, Room Display, resto app): `room_charge` needs a `booking_id`, `unpaid` skips validation + folio, anything else is checked against the property's real `payment_methods` table. Room Display room-service orders are unaffected — they still go `room_charge` + confirm queue.
- **Backend:** `server/routes/resto.js` (staff surface) + `server/routes/restoGuest.js` (guest QR surface), both gated `moduleGuard('resto_ordering')` per-route rather than at the `app.use` mount (same reason as `/api/kitchen`/`/api/calls`). `server/services/tableSessionService.js` (session open/close/summary) and the confirm/reject logic in `resto.js` (rejecting restores stock via a compensating `stock_movements` row and nulls `kitchen_status` so a rejected order can never resurface on the kitchen board). Revenue aggregates (`reports.js`, `dashboard.js`, `nightAudit.js`) exclude `confirmation_status='rejected'` rows; the PMS sales list (`routes/sales.js`) deliberately does not, so staff can still see declined orders there.
- **Menu and table management live in resto-display too, not just the PMS**: `MenuManagementScreen.jsx` (`/staff/menu`, `resto_menu` permission) adds/edits `products` directly — the exact same `/api/products` endpoints the PMS Sales page's Products tab uses, so a menu item created either place shows up everywhere immediately. `TablesScreen.jsx`'s "+ Add Table" posts to `/api/tables` the same way. Both reuse existing shared routes rather than duplicating product/table CRUD inside `routes/resto.js`.
- **Stack:** React/Vite PWA (`resto-display/`), dev port 5178, CORS origin via `RESTO_URL` env var, printable per-table QR sheet via `qrcode` (`TableQrSheet.jsx`). Deployed at `resto.zahill.kdai.cloud` per `nginx/resto.conf`, same domain-deferral note as Kitchen Display above. `RESTO_PUBLIC_URL` builds the absolute QR link (falls back to `RESTO_URL`'s first origin).
- **Existing `/sales` PMS page and its dine-in flow are untouched** — this is additive. A property without the module keeps exactly what it has today.
- **Front desk / restaurant catalog split (interim) — implemented 2026-09-22.** Raised directly: `products`/`sales` is one shared table used by both `Sales.jsx` (front desk's ancillary-charges tool — extra bed, merchandise, tours, misc fees) and the whole F&B stack (Kitchen Display, Room Display's "Order Food", resto-display's staff/guest ordering, `MenuManagementScreen.jsx`) — with no separation, a food item could show up in front desk's POS grid and, worse, a front-desk-only item (e.g. "Extra Bed") could show up in a guest's room-service or table QR menu as something orderable. **This pass is a UI/read-path-level fix, not a schema change** — a real separate table for restaurant vs. front-desk items is scoped as its own, larger, separately-planned migration (touches `sale_items`/`stock_movements`/`purchase_order_items`'s FKs, `salesService.createSale`'s one choke point, and 10 route/service files — see "Open Decisions" below). For now:
  - `routes/display.js`'s `GET /room/:roomId/menu` (guest "Order Food"), `routes/resto.js`'s `GET /menu` + its category list, and `routes/restoGuest.js`'s guest QR `GET /menu` all now filter `WHERE category IN ('drinks','food')` unconditionally — these three endpoints exist only to sell food/drinks, so the scope is correct regardless of module state, not conditional on anything.
  - `Sales.jsx` hides `drinks`/`food` (Sell tab grid, Products tab list, and the add/edit-product category dropdown) whenever `hasModule('resto_ordering')` — a property without Resto Ordering enabled keeps the full, unfiltered single-POS experience exactly as before. A subtitle explains the split when it's active ("Drinks & food are sold through the restaurant app...").
  - `resto-display/src/screens/MenuManagementScreen.jsx` (which calls the shared, unfiltered `/api/products` CRUD list directly) now scopes its own `CATEGORIES` constant to `['drinks','food']` only — so it never lists, edits, or lets staff create a front-desk item either, mirroring `Sales.jsx`'s restriction in the other direction.
  - Back Office (Purchasing/Inventory Value) is deliberately **not** filtered — it's a cross-category owner financial view and correctly needs to see every item regardless of catalog origin.
  - Verified against the live dev DB with real HTTP round-trips: created one `food` and one `other` test product, confirmed all three F&B ordering endpoints return only the food item, confirmed the `Sales.jsx` filtering logic (simulated against the real data) shows only the non-food item when `resto_ordering` is on and both when it's off. Test data and temporarily-toggled modules fully reverted afterward.
- **Deliberately not built this pass:** auto-close of idle table sessions (revisit if forgotten tables become a real problem — natural follow-up is a `closeStaleSessions()` job on the existing nightly job runner, same pattern as night audit's auto-no-show), a separate credential store for floor staff (rejected in favor of reusing PMS users/roles), and COGS/recipe costing (belongs to the separate, not-yet-started `back_office` module — see Open Decisions below).

## Important Conventions

- **Every new table needs `property_id`** (unless it's genuinely platform-global, like `properties` itself or superadmin-only tables) — and every route touching it needs `WHERE property_id = $n` on every SELECT/INSERT/UPDATE/DELETE. This is the single easiest thing to forget when adding a feature; it's the difference between multi-tenant and a data leak between clients.
- **Relays are generic** — `relay_1`...`relay_N` in firmware/DB. Human-readable labels live in `unit_relays`. Never hardcode relay purposes in firmware.
- **Room IDs** — ESP32 uses simple string IDs, mapped via `units.controller_id`.
- **No localStorage in PWA artifacts** — use React state or backend for persistence (exception: Room Display's own device-local room ID/token, which is intentionally local to that physical tablet).
- **CommonJS in server** — `require()`, not `import`. Do not convert to ESM.
- **Migrations** — numbered SQL files in `server/db/migrations/`. Check the migrations table above (or the actual highest-numbered file on disk) for the next number rather than trusting a restated number here — update the "Next migration number" line in both this file and `ROADMAP.md` when you add one.
- **New features that touch routes must consider**: does this need a new module in `server/modules.js`? Does it need `property_id` scoping? Should the migration number and this file's migration table both be updated in the same commit?
- **New module-gated client pages need `RequireModule` on the route, not just a `hasModule()` check in the nav** — `client/src/App.jsx`'s route list and `client/src/components/Sidebar.jsx`/`BottomNav`'s nav-visibility checks are two separate places that must agree; it's easy to add one and forget the other (this was a real, multi-route bug fixed in one pass — see `git log` around the sidebar redesign).

## Working Across Multiple Machines (laptop + PC)

Since development happens on two machines, **this file and `ROADMAP.md` are the handoff mechanism** between them — not memory, not chat history. Treat doc updates as part of the feature, not cleanup afterward.

**Every time you (or Claude) finish a feature, migration, or architectural change:**
1. Update `ROADMAP.md` — flip the status, bump "Next migration number" if a migration was added.
2. Update this file (`CLAUDE.md`) if the change affects: routes, migrations table, module registry, module list, env vars, naming conventions, or known gaps.
3. Commit docs **in the same commit** as the code change, not a separate "docs" commit later — it's too easy to skip that second commit.
4. `git push` before walking away from either machine.

**Releasing to `main`:** `git checkout main && git merge --ff-only dev && git push`. Don't cherry-pick — `main` and `dev` were rejoined on 2026-09-26 (`bb29936`) after cherry-picked releases had left them with the same code under different commit ids; `main` should always be a fast-forward of `dev`. If `--ff-only` refuses, something was committed straight to `main` — merge `main` into `dev` first.

**Starting a session on either machine:**
1. `git pull` first, always — don't trust memory of "where things were."
2. Re-read this file's Multi-Tenancy and Roadmap Status sections if it's been more than a few days.
3. Run `npm run migrate` in `server/` if migrations were added on the other machine — check the migrations table above against what's actually applied in your local DB if unsure.
4. `npm install` in `client/` and `server/` if `package.json`/lockfiles changed.
